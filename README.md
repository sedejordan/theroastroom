# The Roast Room

The Roast Room is an interactive football banter site. Supporters pick a rival club and
read funny, embarrassing and painful facts about it. Every published roast is backed by
dated evidence that a human has checked.

The site launches with Manchester United live. Arsenal, Liverpool, Manchester City,
Chelsea and Tottenham Hotspur are listed as coming soon.

It is built by the solo web agency Fritt and doubles as a portfolio piece, so the code is
kept small, readable and easy to extend.

## Stage 1 scope

This repository holds stage 1 only: project structure, design tokens, the theming system,
the club registry, the roast schema, validation, a developer token preview page and this
documentation.

Not built yet: the landing page, the roast generator, share cards and the suggestions form.
There is no real roast content in the repository and there will not be until the content
stage.

## Requirements

- Node 18 or later
- npm

The only development dependency is Tailwind CSS, pinned to the 3.4 line.

## Run it locally

```bash
npm install
npm run css
npx serve .
```

Then open the URL that `serve` prints.

`fetch` needs an http origin, so opening `index.html` from the file system will not load
the registry. If you would rather not install `serve`, the Python standard library works:

```bash
python3 -m http.server 8000
```

## Scripts

| Script | What it does |
| --- | --- |
| `npm run css` | Compiles `src/input.css` to `dist/styles.css` once |
| `npm run watch` | Compiles the CSS and rebuilds on every change |
| `npm run validate` | Validates the registry and every club data file, exits 1 on any problem |
| `npm test` | Runs the schema tests with the Node test runner |

## Design tokens and theming

Every colour lives in `css/tokens.css` as a CSS custom property on `:root`. The default
values are the Manchester United theme.

`tailwind.config.js` does not contain literal colours. It maps Tailwind colour keys such as
`background`, `surface` and `primary` onto `var(--colorBackground)` and so on. Swapping a
club theme is therefore a CSS variable swap, not a rebuild:

```js
import { applyTheme } from './js/theme.js';

applyTheme({ primary: '#EF0107', accent: '#063672' });
```

`applyTheme` clears every theme property from the root first and then sets only the keys
you pass, so a coming soon club can ship two colours and inherit the rest from the default
theme. `clearTheme()` does the same reset without applying anything, and both functions
keep the `theme-color` meta tag in step.

Other token groups:

- A fluid type scale built on `clamp`, with line height and letter spacing tokens
- A quarter rem spacing scale
- Small radii for a scoreboard feel
- Border width, minimal shadow and z index tokens
- Motion durations and easing curves that collapse to 1ms under `prefers-reduced-motion`

Contrast was checked against the background token: body text is 18.2 to 1, muted text is
7.6 to 1, and accent text is 15.0 to 1. The primary red is 4.1 to 1, so it is used for
large text, borders and fills only, never for small body copy.

## Club registry

`data/clubs.json` is the single source of truth for which clubs exist.

```json
{
  "id": "manutd",
  "name": "Manchester United",
  "shortName": "Man United",
  "status": "live",
  "dataFile": "data/clubs/manutd.json",
  "themeKey": "manutd"
}
```

- `status` is either `live` or `comingSoon`
- `dataFile` is required when the club is live and is not needed before then
- `themeKey` ties the club to its theme
- A coming soon club carries a `theme` object with an approximate `primary` and `accent`

A club data file carries the club metadata, the full theme, the categories the club exposes
and a `roasts` array.

## Roast schema

Every roast must satisfy all of the following:

| Field | Rule |
| --- | --- |
| `id` | Lowercase letters, digits and underscores, unique inside the club |
| `clubId` | Must match the club that owns the data file |
| `category` | Must exist in that club categories array |
| `headline` | The joke, 90 characters or fewer |
| `explanation` | Plain factual context, 280 characters or fewer |
| `evidence` | At least one item |
| `evidence[].claim` | A precise factual statement |
| `evidence[].period` | A season such as `2013/14` or a date such as `2021/09/11` |
| `evidence[].sourceName` | The publication or record the claim came from |
| `evidence[].sourceUrl` | Absolute URL starting with `https` |
| `evidence[].accessedOn` | Real calendar date the source was read, formatted `YYYY/MM/DD` |
| `verified` | Boolean, and it must be `true` for the roast to be published |
| `verifiedOn` | Required when `verified` is true, formatted `YYYY/MM/DD` |
| `tags` | Optional array of strings |

A roast with no evidence, a non https URL, a missing period or `verified` set to `false` is
never displayed. Dates are validated against the real calendar, so `2024/02/31` and
`2023/02/29` are rejected while `2024/02/29` is accepted.

**FAKE example. This is placeholder data that exists only to show the shape. It is not a
football fact and it must never ship.**

```json
{
  "id": "fake_example_roast",
  "clubId": "fakeclub",
  "category": "trophyDroughts",
  "headline": "FAKE headline used to show the schema shape.",
  "explanation": "FAKE explanation used to show the schema shape.",
  "evidence": [
    {
      "claim": "FAKE claim used to show the evidence shape.",
      "period": "2013/14",
      "sourceName": "FAKE Source Name",
      "sourceUrl": "https://example.com/fakeSource",
      "accessedOn": "2024/01/15"
    }
  ],
  "verified": true,
  "verifiedOn": "2024/01/16",
  "tags": ["fake"]
}
```

## Content accuracy rules

1. Never invent a fact, a score, a statistic, a date or a URL.
2. Every claim needs a named source and a live `https` URL.
3. Every claim records the period it refers to, so the reader knows the context.
4. A roast is published only when a human has set `verified` to `true` and dated it.
5. If a fact cannot be sourced, the roast is cut. It is not softened or hedged.
6. Sample and test data is labelled FAKE and is never loaded by the site.

The browser drops invalid roasts and logs a console warning with the roast id and the
reasons. The data gate is strict and fails the build.

## Adding a new club

The three steps below each leave the repository in a state where `npm run validate`
passes, so you can pause at any step.

1. Add the club to `data/clubs.json` with `id`, `name`, `shortName`, `status` set to
   `comingSoon`, `themeKey` and a `dataFile` path. A coming soon club may declare a
   `dataFile` that does not exist yet, so validation passes with the file still missing.
2. Create `data/clubs/<clubid>.json` with the club metadata, the full theme object, the
   categories array and an empty `roasts` array. The coming soon club now has a valid data
   file that is validated exactly like a live club file.
3. Run `npm run validate` and `npm test`. When both pass, change the registry status from
   `comingSoon` to `live` and run `npm run validate` again to confirm the live club still
   has an existing, valid data file.

The orphan rule is strict: every file in `data/clubs` must be referenced by a `dataFile`
path on some registry entry, whatever the status of that entry. A data file that no
registry entry references fails validation.

No JavaScript changes are needed. The registry drives the lists, the theme tokens drive the
colours and the loaders pick the new club up automatically.

## Accessibility and performance

- Semantic landmarks, a skip link, a `lang` attribute and one `h1` per page
- Visible focus rings driven by tokens, never colour alone
- Colour contrast checked against WCAG AA
- All motion runs through duration tokens and collapses under `prefers-reduced-motion`
- Fonts load with `preconnect` and `display=swap`, and every stack has a system fallback
- No frameworks, no bundlers and one development dependency

## Validation and tests

```bash
npm run validate
npm test
```

`npm run validate` fails on an invalid roast, a duplicate roast id, an unknown category, an
unknown club, a live club with no data file, an unreadable live data file, an invalid data
file on a coming soon club that declares one, an orphaned data file that no registry entry
references, or a malformed registry. `npm test` covers each schema rule with FAKE fixtures
